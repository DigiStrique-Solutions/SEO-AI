# Generic On-Page SEO Checklist

Updated: 2026-06-29

Use this checklist for a generic page-level SEO audit before applying deeper vertical checklists such as ecommerce, lead gen, or app installs. It is intentionally broad. Skip items that do not apply to the page type, but do not delete them from the master checklist.

2026-specific notes:

- Google clarified in May 2026 that Search spam policies also apply to attempts to manipulate generative AI responses in Google Search. Do not create pages or markup designed to game AI answers.
- Google deprecated FAQ rich results from Search starting May 7, 2026. FAQ content can still be useful for users, and FAQPage remains a valid Schema.org type, but it should not be treated as a Google rich result tactic.
- Google's AI guidance says the foundation is still normal SEO: helpful content, crawlability, eligibility for snippets, page experience, and user value. Do not require `llms.txt`, AI-only markup, or special machine-readable files for Google AI visibility.
- `Google-Extended` is not a control for Google AI Overviews or AI Mode. Use normal Search snippet and preview controls where Google documents them.
- Core Web Vitals good thresholds remain LCP under 2.5s, INP at or below 200ms, and CLS at or below 0.1.
- Google does not define a fixed character limit for title tags or meta descriptions. Treat length as a display and clarity check, not a ranking formula.
- Google does not have a preferred word count for blog posts or pages. Content should be as long as needed to satisfy the user intent, and no longer.

## Scoring

Use this severity model:

- `critical`: blocks crawling, indexing, rendering, trust, legal compliance, or primary conversion.
- `high`: materially weakens relevance, quality, snippet eligibility, or user experience.
- `medium`: improves clarity, completeness, or discoverability, but is not blocking.
- `low`: polish, maintenance, or optional enhancement.
- `not_applicable`: page type does not need this item.

For each issue record:

```text
Severity:
Page or URL:
Evidence:
Why it matters:
Fix:
Owner:
Confidence:
Source:
```

## Evidence Source Legend

Use free, owned, or open-source sources first. Do not depend on DataForSEO, Semrush, Ahrefs, Moz, or other paid SEO databases for the generic v1 checklist.

Google-visible scope: judge pass/fail from public rendered evidence, HTTP responses, robots/sitemaps, GSC outcome data, and lab/field performance evidence. CMS/code, PostHog/GA4, governance, ownership, logs, and editorial workflow are optional implementation or prioritization evidence, not blockers for what Google can see.

- `Firecrawl`: public crawl, rendered extraction, raw HTML, metadata, links, images, screenshots, and simple browser actions.
- `Playwright`: precision rendering, DOM assertions, screenshots, mobile viewport checks, authenticated/local pages, console and network debugging.
- `GSC`: Google Search Console performance, indexing, sitemaps, URL Inspection, search appearance, and Crawl Stats where available.
- `GA4`: landing page traffic, engagement, conversions, revenue or lead events.
- `GKP`: Google Ads Keyword Planner for keyword ideas and directional search demand.
- `GBP`: Google Business Profile for local profile, location, review, and local performance context.
- `GMAPS`: Google Maps Places for place details, local competitors, categories, photos, and address metadata.
- `GMC`: Google Merchant Center or Merchant API for product/feed/shipping/returns/merchant listing data.
- `LH`: Lighthouse CLI, Lighthouse Node runner, or Lighthouse CI for lab performance, accessibility, best practices, and SEO diagnostics.
- `CrUX`: Chrome UX Report API for public field Core Web Vitals at URL or origin level.
- `OSS`: free/open-source tooling such as Schema.org validator, axe-core, HTML validator, link checker, sitemap parser, robots parser, image tooling, `web-vitals`, or sitespeed.io.
- `CMS/code`: WordPress, Shopify, Webflow, GitHub/codebase, server logs, CDN logs, or sitemap/robots files owned by the customer.
- `Monitoring`: uptime monitor, status page, error monitor, CDN/WAF events, server response monitor, and deploy checks owned by the customer.
- `Manual/free SERP`: manual SERP review, user-provided screenshots, GSC search appearance, or free search surfaces. Avoid building a paid SERP dependency in v1.
- `Human/context`: product marketing context, customer input, editorial judgment, legal/compliance review, or subject-matter expert review.

## 1. Page Intent And Role

Evidence sources: `GSC`, `GA4`, `GKP`, `Firecrawl`, `Playwright`, `Human/context`.

- [ ] The page has one clear primary search intent.
- [ ] The page type is identified: homepage, service page, product page, collection page, blog post, comparison page, alternative page, documentation page, local page, category page, landing page, pricing page, support page, or tool page.
- [ ] The page has one clear business goal: traffic, lead, signup, purchase, app install, trial, support deflection, retention, or brand trust.
- [ ] The target audience is explicit enough to shape copy, examples, objections, and CTAs.
- [ ] The page maps to one primary topic or keyword theme, not several competing intents.
- [ ] Secondary topics support the primary intent instead of turning the page into a generic catch-all.
- [ ] The page is not cannibalizing another page with the same intent.
- [ ] The page has a clear next step for users who are ready to act.
- [ ] The page has a clear next step for users who are still researching.

## 1A. Site Architecture And Navigation

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `GA4`, `GKP`, `CMS/code`, `Human/context`, `OSS`.

- [ ] For full site-wide architecture review, load the dedicated checklist: [Site Architecture SEO Checklist](site-architecture-seo-checklist.md).
- [ ] The site type is identified before judging architecture: SaaS marketing, content/blog, ecommerce, documentation, hybrid, small business, local, marketplace, or app install site.
- [ ] A content inventory exists or can be generated from crawl, sitemap, CMS, and analytics data.
- [ ] Priority pages are identified by traffic, conversions, revenue, leads, strategic importance, and search opportunity.
- [ ] The site has a clear hierarchy from homepage to primary sections, section hubs, detail pages, and conversion pages.
- [ ] Important pages are reachable from the homepage or relevant hubs within a shallow click depth.
- [ ] Navigation reflects user tasks and business priorities, not only internal org structure.
- [ ] Primary navigation is concise enough to scan and does not hide critical sections behind unclear labels.
- [ ] Header, footer, sidebar, breadcrumb, contextual, and related-content navigation each have a clear role.
- [ ] Hub pages exist for major topics, categories, products, services, docs, or resource areas where the site has multiple related pages.
- [ ] Hub pages link to important child pages and child pages link back to their parent hub where useful.
- [ ] Taxonomies, categories, tags, collections, and filters are controlled so they create useful paths rather than thin duplicate archives.
- [ ] URL paths, breadcrumbs, and visible navigation describe the same hierarchy.
- [ ] Page templates support unique titles, H1s, intros, internal links, schema, and CTAs for each page type.
- [ ] Conversion pages are accessible from relevant informational and commercial pages.
- [ ] Support, legal, account, and utility sections are separated from acquisition-focused sections where possible.
- [ ] The architecture can be represented as an ASCII tree or visual sitemap for review.

## 2. Crawlability

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `CMS/code`, `OSS`.

- [ ] The page is reachable through normal HTML links, not only search, filters, JavaScript actions, forms, or internal APIs.
- [ ] Important links use valid `href` values that crawlers can discover.
- [ ] Navigation, breadcrumbs, related content, and pagination expose crawlable URLs.
- [ ] The page is not blocked by `robots.txt` if it should rank.
- [ ] The page's critical CSS, JavaScript, image, and API resources are not blocked in a way that prevents rendering or content discovery.
- [ ] The page is linked from at least one relevant internal page.
- [ ] The page is no more than 3 clicks from an important hub when it is a priority page.
- [ ] The page is included in the relevant XML sitemap if it is canonical and indexable.
- [ ] The sitemap entry uses the canonical URL, returns a successful status, and is not blocked or noindexed.
- [ ] The page is discoverable by Bing as well as Google when Bing traffic matters.
- [ ] Paginated series expose unique crawlable URLs for each page, use sequential links with real `href` values, and avoid URL fragments for page numbers.
- [ ] Infinite scroll or "load more" experiences have crawlable paginated URLs or equivalent linked pages.
- [ ] Faceted and filtered URL patterns are classified as indexable or non-indexable before audit recommendations are made.
- [ ] Nonvaluable facet combinations are controlled to avoid crawl traps, duplicate pages, and empty result pages.
- [ ] For large, fast-changing, or heavily parameterized sites, Search Console Crawl Stats or server logs are reviewed for wasted crawl on redirects, 404 or 410, soft 404s, 5xx or 429 responses, and low-value parameter paths.
- [ ] When logs, bot allowlists, or firewall rules are used as evidence, Googlebot is verified by reverse DNS or official IP ranges rather than user-agent strings alone.

## 3. Indexability

Evidence sources: `GSC`, `Firecrawl`, `Playwright`, `CMS/code`, `OSS`.

- [ ] The page returns a valid indexable response when it should rank.
- [ ] The page does not have `noindex` in a robots meta tag or X-Robots-Tag header unless intentionally excluded.
- [ ] Thank-you, confirmation, checkout success, form success, unsubscribe, login, password reset, account, cart, internal search result, and other utility pages are reviewed for whether they should rank.
- [ ] Utility pages that should not rank use `noindex` through a robots meta tag or X-Robots-Tag header.
- [ ] Utility pages that use `noindex` are not blocked by `robots.txt`, because crawlers must be able to crawl the page to see the `noindex` directive.
- [ ] Utility pages that should not rank are excluded from XML sitemaps and acquisition-focused internal linking.
- [ ] Sensitive utility pages are protected by authentication or authorization. Do not rely on `robots.txt` for privacy or access control.
- [ ] The page does not use `nosnippet`, `max-snippet`, `max-image-preview`, or `max-video-preview` in a way that harms the desired search appearance.
- [ ] The canonical URL points to the preferred version of this page.
- [ ] Unique pages use self-referencing canonicals.
- [ ] Near-duplicate pages canonicalize to the best representative URL.
- [ ] Canonical tags are not contradictory with redirects, hreflang, sitemap URLs, or internal links.
- [ ] The canonical URL returns a successful response and is not noindexed or blocked.
- [ ] The page is not a soft 404: thin, empty, unavailable, or error-like content returning 200.
- [ ] If the page is removed permanently, it returns 404 or 410 rather than redirecting every missing URL to the homepage.
- [ ] If the page moved permanently, it redirects with a permanent redirect to the closest matching replacement.
- [ ] PDFs, documents, images, feeds, and other non-HTML assets are reviewed for whether they should be indexed.
- [ ] Non-HTML assets that should not be indexed use `X-Robots-Tag` or access control where appropriate.
- [ ] Non-HTML duplicates use HTTP canonical headers where needed.

## 4. URL And Page Identity

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `CMS/code`, `OSS`.

- [ ] The URL is readable, stable, lowercase, and uses hyphens between words.
- [ ] The URL reflects the page topic without keyword stuffing.
- [ ] The URL does not expose unnecessary parameters, sessions, sorting states, tracking IDs, or internal IDs.
- [ ] The preferred protocol, host, trailing slash, and casing are consistent.
- [ ] HTTP redirects to HTTPS.
- [ ] Non-preferred host variants redirect to the preferred host.
- [ ] Parameter variants are controlled by canonicalization, internal linking hygiene, and crawl rules where needed.
- [ ] Redirects use the correct permanent or temporary status for the intent.
- [ ] Redirect chains and loops are avoided.
- [ ] Internal links, canonicals, hreflang, and sitemaps point directly to the final preferred URL instead of an old redirecting URL.
- [ ] The page has a stable content identity across mobile and desktop.
- [ ] The page can be shared, bookmarked, crawled, and rendered directly at its URL.
- [ ] Search result attribution is recognizable for branded and priority pages: site name, favicon, homepage `WebSite` structured data, and brand naming are consistent.

## 4A. Technical Infrastructure And Production Health

Evidence sources: `GSC`, `Firecrawl`, `Playwright`, `LH`, `CMS/code`, `OSS`, `Monitoring`, `Human/context`.

- [ ] HTTPS is enabled for all public canonical pages.
- [ ] TLS certificate is valid, trusted, covers the right hostnames, and is monitored before expiry.
- [ ] HTTP redirects to HTTPS with the intended redirect status.
- [ ] Mixed content is not present on rendered pages.
- [ ] HSTS is reviewed for production sites where forced HTTPS is safe for the domain and subdomains.
- [ ] CDN, firewall, WAF, bot protection, rate limits, and geo rules do not block important users, Googlebot, GSC fetchers, AdsBot, Merchant Center, or other required crawlers.
- [ ] Googlebot handling is verified with reverse DNS or official Google IP ranges, not only user-agent strings.
- [ ] Important pages do not return unexpected 4xx, 5xx, 429, timeout, DNS, TLS, or connection errors.
- [ ] Uptime, server response, and error-rate monitoring exist for templates and sections that matter to organic traffic.
- [ ] GSC Crawl Stats or server/CDN logs are reviewed for large, fast-changing, or heavily parameterized sites.
- [ ] Crawl budget issues are investigated only when the site scale or crawl behavior justifies it.
- [ ] Staging, preview, QA, dev, and test environments are blocked by authentication or network controls, not only robots.txt.
- [ ] Staging or preview pages are not accidentally canonicalized from production pages.
- [ ] Accidental indexation of non-production URLs is checked in GSC, logs, and manual search where relevant.
- [ ] Search Console Manual Actions and Security Issues are checked before major SEO recommendations.
- [ ] Hacked content, malware, phishing, injected spam, and suspicious outbound links are escalated as security issues, not normal SEO tickets.
- [ ] Migration launches include pre-launch crawl, redirect map, canonical and sitemap checks, robots/noindex cleanup, GSC validation, analytics annotation, and post-launch crawl.
- [ ] Post-migration monitoring checks redirects, 404 or 410, soft 404s, 5xx, 429, sitemap coverage, indexation, traffic, and conversion impact.
- [ ] Template-level deploy checks validate rendered title, meta description, canonical, robots, hreflang, schema, headings, internal links, status code, and primary content.
- [ ] Deploy regressions are sampled across important templates, not only the homepage.

## 5. Title Link Inputs

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `Manual/free SERP`, `CMS/code`.

- [ ] The `<title>` element exists and is unique.
- [ ] The title accurately describes the page.
- [ ] The primary topic appears naturally near the beginning when it helps users.
- [ ] The title is not stuffed with repeated keywords, locations, brands, or separators.
- [ ] The title is not vague, boilerplate, or reused across templates.
- [ ] The visible H1, main heading, and title are aligned enough that Google is less likely to rewrite the title link.
- [ ] The brand is included when it clarifies trust or avoids ambiguity.
- [ ] The title fits the page type: comparison, guide, product, category, pricing, tool, or service.
- [ ] The title is written for click clarity, not just ranking.
- [ ] The title is concise enough for search result display, but not forced into a fixed character count.
- [ ] Long or verbose titles are shortened when they bury the main topic, repeat boilerplate, or make truncation likely on common devices.
- [ ] The observed Google title link is compared with the intended `<title>` for priority queries.
- [ ] If Google rewrites the title poorly, competing headings, boilerplate title text, internal anchor text, off-page anchors, and query mismatch are reviewed.

## 6. Meta Description And Snippet Inputs

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `Manual/free SERP`, `CMS/code`.

- [ ] A unique meta description exists for priority pages.
- [ ] The description accurately summarizes what the user will get on the page.
- [ ] The description includes the main value, use case, or differentiator.
- [ ] The description does not promise content, pricing, availability, or benefits that are absent from the page.
- [ ] The description is not duplicated across many URLs.
- [ ] The page's visible intro, headings, and summary sections can produce a good snippet even if Google ignores the meta description.
- [ ] The page includes concise answerable passages for informational queries.
- [ ] Dates, prices, availability, ratings, and claims in snippets are kept current where shown.
- [ ] `data-nosnippet` is used only where snippets must hide sensitive or poor-fit text.
- [ ] Meta descriptions are long enough to be useful, but not padded to hit a fixed character count.
- [ ] Long meta descriptions put the most important value, entity, or differentiator early because snippets may truncate to device width.
- [ ] The observed Google snippet is compared with the intended description and visible page summary for priority queries.
- [ ] For priority queries, live SERP features or Search Console search appearance are reviewed to identify addressable elements such as rich results, images, videos, breadcrumbs, sitelinks, and product results.

## 7. Headings And Semantic Structure

Evidence sources: `Firecrawl`, `Playwright`, `CMS/code`, `OSS`.

- [ ] The page has one clear visible H1 that names the page's core topic.
- [ ] H2s and H3s form a logical outline.
- [ ] Headings are not used only for visual sizing.
- [ ] Heading text uses human-readable language rather than stuffed keyword variants.
- [ ] The first screen makes the topic, audience, and value clear.
- [ ] The page uses semantic HTML where practical: `main`, `nav`, `article`, `section`, `header`, `footer`, and lists or tables where appropriate.
- [ ] The main content is not hidden behind tabs, accordions, carousels, or client-only rendering in a way that weakens discovery.
- [ ] Boilerplate, ads, widgets, popups, and unrelated modules do not overwhelm the main content.
- [ ] The page is usable without relying on images of text.
- [ ] Long pages use stable section IDs and in-page navigation where helpful.
- [ ] JavaScript does not break URL fragments, deep links, or direct access to target sections.

## 8. Content Usefulness And Quality

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `GA4`, `Human/context`, `OSS`.

- [ ] For deep content review, load the dedicated checklist: [Content SEO Checklist](content-seo-checklist.md).
- [ ] The page satisfies the query better than a thin summary or generic rewrite.
- [ ] The page includes original insight, firsthand experience, proprietary data, expert review, examples, or concrete implementation detail.
- [ ] The page clearly answers who it is for and what problem it solves.
- [ ] The content is current for the topic and shows last updated or reviewed dates when freshness matters.
- [ ] Claims are supported by evidence, screenshots, examples, data, citations, or product facts.
- [ ] The page avoids unsupported superlatives such as "best", "number one", or "guaranteed" unless substantiated.
- [ ] Blog posts and articles are not written to a fixed word count. They are as short as possible while fully satisfying the intent.
- [ ] Short pages are not flagged only because they are short; they are flagged only when they fail to answer the intent, lack evidence, or create thin/duplicate value.
- [ ] Long pages are not considered better only because they are long; filler, repeated points, and irrelevant sections are removed.
- [ ] Paragraphs are short, scannable, and usually focused on one idea.
- [ ] Dense passages are broken up with useful headings, bullets, tables, examples, summaries, or visuals where that helps comprehension.
- [ ] The page does not exist only to capture traffic with no useful user value.
- [ ] The page avoids doorway patterns: many near-identical pages targeting tiny keyword or location variants without unique value.
- [ ] The page avoids scaled content abuse: many pages generated at scale without real usefulness, review, or differentiation.
- [ ] The page avoids site reputation abuse: third-party or off-topic content published mainly to exploit the host domain's ranking signals.
- [ ] The page does not contain hidden text, hidden links, cloaked content, or deceptive redirects.
- [ ] AI-assisted content has human editorial judgment, fact checking, and added value.
- [ ] The "who, how, and why" of content creation is clear when trust matters.
- [ ] Templated page types are sampled across multiple URLs to detect repeated titles, descriptions, H1s, intros, schema, CTAs, and boilerplate.
- [ ] Clear YMYL pages are classified by harm type, such as health, safety, financial security, civics, or societal welfare, and require stronger review before publication recommendations.

## 9. Topical Coverage

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `GKP`, `Human/context`, `Manual/free SERP`.

- [ ] The page covers the user's main question or task completely.
- [ ] The page includes necessary definitions, context, steps, comparisons, risks, examples, and next actions.
- [ ] The page answers adjacent questions a searcher is likely to ask next.
- [ ] The page links to deeper supporting content rather than trying to answer every subtopic inline.
- [ ] The page includes entity clarity: product names, categories, people, organizations, locations, standards, tools, and attributes are unambiguous.
- [ ] The page distinguishes facts, recommendations, opinions, and assumptions.
- [ ] The page handles objections or decision criteria where conversion matters.
- [ ] The page is not artificially lengthened for SEO.
- [ ] The page is not too thin for its intent.

## 10. Keyword And Query Mapping

Evidence sources: `GSC`, `GKP`, `GA4`, `Firecrawl`, `Manual/free SERP`.

- [ ] The primary query theme is mapped to this page and not another stronger page.
- [ ] The page naturally includes important synonyms, entities, and modifiers.
- [ ] Exact-match keyword repetition is not forced.
- [ ] The page includes the language users actually use, not only internal product jargon.
- [ ] Search intent is classified: informational, commercial, transactional, navigational, local, support, or mixed.
- [ ] SERP expectations are matched: guide, list, tool, category, comparison, video, product, local results block, image-heavy result, or short answer.
- [ ] If the query has local intent, location signals are visible and accurate.
- [ ] If the query has commercial intent, proof, pricing, alternatives, and decision support are present.
- [ ] If the query has support intent, the page is direct and task-focused.

## 11. Internal Linking

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `CMS/code`, `OSS`.

- [ ] The page receives links from relevant hub, category, navigation, or high-authority pages.
- [ ] The page links out to closely related child, parent, sibling, and conversion pages.
- [ ] Anchor text is descriptive and concise.
- [ ] Anchor text sets accurate expectations for the destination page.
- [ ] Repeated internal links are not spammy or mechanically exact-match.
- [ ] Important links are visible in rendered HTML, not only injected after user interaction.
- [ ] Breadcrumbs are present when the page sits in a hierarchy.
- [ ] Pagination, faceted navigation, or related collections avoid creating crawl traps.
- [ ] Orphan pages are identified and fixed.
- [ ] Broken internal links are fixed or removed.

## 12. External Links And Citations

Evidence sources: `Firecrawl`, `Playwright`, `OSS`, `Human/context`.

- [ ] Factual claims link to authoritative supporting sources when appropriate.
- [ ] External links are relevant, useful, and not included only for reciprocal or manipulative reasons.
- [ ] Affiliate, sponsored, paid, or user-generated links use the correct `rel` attributes where needed.
- [ ] Outbound links open a useful path for the reader, not a distraction from the page goal.
- [ ] External citations are not stale for time-sensitive claims.
- [ ] The page does not sell or exchange links in ways that violate search policies.

## 13. Images

Evidence sources: `Firecrawl`, `Playwright`, `LH`, `CMS/code`, `OSS`.

- [ ] Important images are relevant to the surrounding text.
- [ ] Informative images have descriptive alt text that conveys meaning, not keyword stuffing.
- [ ] Decorative images use empty alt text or CSS background treatment where appropriate.
- [ ] Image filenames are descriptive when practical.
- [ ] Images have explicit width and height or reserved layout space to prevent layout shift.
- [ ] Images are compressed and served in efficient formats.
- [ ] Responsive image variants are used where useful.
- [ ] Above-the-fold critical images are not lazy-loaded in a way that delays LCP.
- [ ] Below-the-fold images are lazy-loaded where appropriate.
- [ ] Image captions or adjacent text clarify charts, screenshots, and product visuals.
- [ ] Image URLs are crawlable if image search visibility matters.
- [ ] Image sitemap or image metadata is considered for large image-heavy sites.
- [ ] Original or licensable images include image license metadata where creator credit, licensing, or image search eligibility matters.
- [ ] Priority editorial or visual pages use relevant high-quality images, with images at least 1200px wide where Discover eligibility matters.
- [ ] Large image previews are allowed unless there is a rights or privacy reason to restrict them.

## 14. Video And Rich Media

Evidence sources: `Firecrawl`, `Playwright`, `LH`, `CMS/code`, `OSS`.

- [ ] Videos support the page intent rather than replacing necessary text.
- [ ] The page includes crawlable text summary or transcript for important video content.
- [ ] Video thumbnails are high quality and crawlable.
- [ ] Video embeds do not severely delay the main content or Core Web Vitals.
- [ ] Video structured data is added when the visible video content qualifies.
- [ ] Video-rich pages have a prominent indexable video or watch page, crawlable thumbnail, and complete `VideoObject` fields such as name, description, thumbnail, upload date, and duration.
- [ ] Key moments or clips are considered only where supported and useful.
- [ ] Audio content has transcripts where search and accessibility matter.
- [ ] Prerecorded video has captions.
- [ ] Video with visual information needed for understanding has audio description or an equivalent media alternative.
- [ ] PDFs or downloads have HTML equivalents when the content should rank.

## 15. Structured Data

Evidence sources: `Playwright`, `Firecrawl`, `GSC`, `GMC`, `GBP`, `CMS/code`, `OSS`.

- [ ] Structured data matches visible page content.
- [ ] Structured data uses a supported type for the page, such as `Article`, `Product`, `Organization`, `LocalBusiness`, `BreadcrumbList`, `ReviewSnippet`, `Event`, `VideoObject`, `Recipe`, or other eligible types.
- [ ] Schema is not added for content that users cannot see.
- [ ] Required and recommended properties are complete for the chosen rich result type.
- [ ] JSON-LD is valid and parsable.
- [ ] Structured data is not blocked, malformed, duplicated, or contradictory.
- [ ] Product, price, availability, ratings, review count, and event dates are current where marked up.
- [ ] Ecommerce structured data covers visible merchant details where applicable, including shipping, return policy, price, availability, variants, reviews, and product identifiers.
- [ ] Review markup follows policy and is not self-serving or fake.
- [ ] Breadcrumb structured data matches visible breadcrumbs.
- [ ] Organization and WebSite markup use stable entity IDs when possible.
- [ ] Subscription, registration-gated, or paywalled indexable content uses correct paywall structured data and is not implemented as cloaking.
- [ ] Forum, Q&A, social, and profile pages use `DiscussionForumPosting`, Q&A, or `ProfilePage` markup only when the visible page type qualifies.
- [ ] FAQPage markup is only used for genuine visible Q&A content. Do not use it for Google FAQ rich results, because that feature is deprecated.
- [ ] Schema is validated with Google's Rich Results Test for Google-supported rich result types.
- [ ] Schema.org validator is used for broader vocabulary validation.
- [ ] Browser rendering is checked before claiming schema is missing, because some CMS plugins inject JSON-LD client-side.

## 16. Mobile-First Readiness

Evidence sources: `Playwright`, `Firecrawl`, `LH`, `GSC`, `CrUX`.

- [ ] Mobile and desktop contain equivalent primary content.
- [ ] Mobile and desktop contain equivalent metadata, canonical tags, robots directives, structured data, hreflang, images, and links.
- [ ] Mobile content is not hidden, truncated, or replaced by app-install interstitials.
- [ ] Text is readable without zooming.
- [ ] Tap targets are large enough and not crowded.
- [ ] The viewport is configured correctly.
- [ ] The page avoids horizontal scrolling.
- [ ] Popups and interstitials do not block the main content.
- [ ] Intrusive interstitials, app-install overlays, cookie banners, newsletter modals, and ads are checked on mobile and do not prevent users from accessing the main content.
- [ ] Mobile navigation exposes important internal links.
- [ ] Mobile rendering is tested with Google's URL Inspection or a real mobile browser.

## 17. Page Experience And Core Web Vitals

Evidence sources: `CrUX`, `LH`, `Playwright`, `Firecrawl`, `GSC`, `GA4`, `OSS`.

- [ ] LCP is under 2.5 seconds for good field performance.
- [ ] INP is at or below 200 milliseconds for good field performance.
- [ ] CLS is at or below 0.1 for good field performance.
- [ ] The likely LCP element is identified and optimized.
- [ ] Server response time does not dominate LCP.
- [ ] Critical CSS and font loading are optimized.
- [ ] Render-blocking scripts are reduced or deferred.
- [ ] Heavy third-party scripts are justified and monitored.
- [ ] Long tasks and hydration costs are reduced where they harm INP.
- [ ] Images, ads, embeds, banners, and dynamic UI reserve layout space.
- [ ] Field data from CrUX or Search Console is preferred over lab-only scores when available.
- [ ] Lab tests are still used to debug root causes.

## 18. JavaScript SEO

Evidence sources: `Playwright`, `Firecrawl`, `GSC`, `CMS/code`, `OSS`.

- [ ] Critical content appears in server-rendered or reliably rendered HTML.
- [ ] Title, meta description, canonical, robots, hreflang, and structured data are available after rendering.
- [ ] Important links render as real anchor links with `href`.
- [ ] Each meaningful route has a unique URL.
- [ ] Single-page apps use the History API for indexable routes rather than hash fragments.
- [ ] Single-page apps return meaningful status handling for missing, private, and moved routes.
- [ ] Client-side route changes update metadata correctly.
- [ ] JavaScript does not create conflicting canonical, robots, hreflang, or structured data tags after hydration.
- [ ] The page does not require user interaction before core content appears.
- [ ] Rendered HTML is compared with raw HTML for important pages.
- [ ] Hydration errors do not remove or alter SEO-critical elements.
- [ ] Lazy loading does not hide in-viewport content from users or rendering tools.
- [ ] JavaScript errors do not prevent crawling, rendering, or interaction.

## 19. Accessibility Signals That Support SEO

Evidence sources: `LH`, `Playwright`, `Firecrawl`, `OSS`.

- [ ] The page has a logical heading order.
- [ ] Links and buttons have accessible names.
- [ ] Images have appropriate text alternatives.
- [ ] Forms have labels, error messages, and accessible instructions.
- [ ] Color contrast supports readability.
- [ ] The page can be navigated by keyboard.
- [ ] The main content is not trapped behind inaccessible controls.
- [ ] Tables are used for tabular data, not layout.
- [ ] Content is readable and understandable at common zoom levels.
- [ ] Text spacing supports readability: line height, paragraph spacing, letter spacing, and word spacing can be increased without losing content or functionality.
- [ ] Body text line length is checked for readability on desktop and mobile, especially on article, blog, and documentation pages.
- [ ] Accessibility fixes prioritize actual user comprehension, not search manipulation.

## 20. Trust, Authorship, And E-E-A-T Inputs

Evidence sources: `Firecrawl`, `Playwright`, `Human/context`, `CMS/code`, `Manual/free SERP`.

- [ ] The page makes the publisher, brand, or organization clear.
- [ ] Author or reviewer information is present when topical trust requires it.
- [ ] Author credentials, practical experience, or editorial review are visible for YMYL or expert content.
- [ ] YMYL pages have visible accountability, source quality, consensus alignment where relevant, and expert review appropriate to the risk.
- [ ] Contact, support, privacy, refund, shipping, legal, or business details are easy to find where relevant.
- [ ] Claims about awards, certifications, customers, results, or guarantees are verifiable.
- [ ] Reviews, testimonials, and case studies are authentic and specific.
- [ ] User-generated content is moderated where quality and safety matter.
- [ ] The page avoids fake expertise, fake authorship, and fake freshness.

## 21. Freshness And Maintenance

Evidence sources: `GSC`, `GA4`, `Firecrawl`, `CMS/code`, `Human/context`.

- [ ] The content is still accurate for current searcher expectations.
- [ ] Time-sensitive data, pricing, screenshots, product names, UI flows, policies, and examples are current.
- [ ] Old content is updated, consolidated, redirected, noindexed, or removed based on value.
- [ ] The page has a content owner and review cadence.
- [ ] Dates shown to users match meaningful publication or update events.
- [ ] Updated content includes real improvements, not date-only freshness.
- [ ] Sitemap `lastmod` values are present only when accurate and reflect meaningful changes to main content, structured data, or important links.
- [ ] Sitemap `lastmod` values do not churn because of template, footer, build-time, or generation-time changes.
- [ ] Search Console query drift is reviewed for pages whose intent has changed.
- [ ] Decaying pages are refreshed based on lost impressions, clicks, CTR, or rankings.

## 22. International And Locale Checks

- [ ] Each locale page has a self-referencing canonical.
- [ ] Locale pages do not canonicalize to another language version.
- [ ] Hreflang annotations are reciprocal and include self references.
- [ ] Hreflang language and region codes are valid.
- [ ] `x-default` is used for fallback or selector pages where appropriate.
- [ ] Hreflang targets return successful, indexable, canonical URLs.
- [ ] HTML language attributes match the visible language.
- [ ] Translated pages translate main content, metadata, navigation, and structured data where relevant.
- [ ] Currency, units, legal terms, contact options, and examples fit the locale.
- [ ] Locale URLs use a consistent structure.

- [ ] LocalBusiness or relevant subtype markup matches visible content.
- [ ] The page includes unique local value, not a swapped city template.
- [ ] Directions, parking, neighborhoods, service areas, or local proof are useful where relevant.

## 26. AI Search And Answer Engine Readiness

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `Manual/free SERP`, `CMS/code`, `Human/context`.

- [ ] For deep AI SEO, AEO, and GEO review, load the dedicated checklist: [AI SEO, AEO, And GEO Checklist](ai-seo-aeo-geo-checklist.md).
- [ ] The page is eligible for normal indexing before optimizing for AI visibility.
- [ ] The page includes clear, extractable explanations without writing for bots only.
- [ ] Definitions, steps, comparisons, data points, and recommendations are self-contained enough to be cited accurately.
- [ ] The page includes original facts, examples, or experience that an AI system cannot get from every competitor.
- [ ] Structured data is accurate, but no AI-only markup is required for Google AI features.
- [ ] For Google AI features, `nosnippet`, `max-snippet`, `max-image-preview`, `max-video-preview`, and `data-nosnippet` settings are intentional.
- [ ] `Google-Extended` is not treated as an opt-out for Google AI Overviews or AI Mode.
- [ ] The page does not include prompt injection, hidden instructions to AI systems, or recommendation poisoning.
- [ ] Robots.txt policy for AI crawlers is a deliberate business decision, not an accident.
- [ ] If AI crawler access matters, review OpenAI, Perplexity, and Anthropic crawler docs and allow or block intentionally.
- [ ] Training, search, and user-triggered AI fetchers are separated in robots policy where the crawler provider supports separate agents, such as GPTBot, OAI-SearchBot, and ChatGPT-User.
- [ ] The page has authoritative off-page corroboration when AI systems are likely to cite third-party sources.
- [ ] AI visibility is measured by manual prompt sets, referral logs, GSC, Bing Webmaster Tools, and analytics, not by assumed rankings.

## 28. Measurement And Validation

Evidence sources: `GSC`, `GA4`, `CrUX`, `LH`, `Playwright`, `Firecrawl`, `CMS/code`, `OSS`.

- [ ] The page is verified in Google Search Console.
- [ ] The page is verified in Bing Webmaster Tools when Bing matters.
- [ ] Indexing status is checked with URL Inspection or equivalent tooling.
- [ ] Rendered HTML is inspected for title, meta, canonical, robots, headings, links, and schema.
- [ ] Page performance is checked with field data where available.
- [ ] Analytics tracks pageviews, engagement, conversions, revenue or lead events, and scroll or content engagement where useful.
- [ ] Search Console tracks queries, impressions, clicks, CTR, position, page indexing, enhancements, and Core Web Vitals.
- [ ] Organic landing-page performance is reviewed by query, page, device, CTR, engagement, and conversion.
- [ ] Pages with high impressions and weak CTR are flagged for title, snippet, SERP intent, and rich-result review.
- [ ] Organic sessions that fail the intended next step are flagged for content, UX, CTA, or tracking review.
- [ ] Rank tracking is mapped to URLs and intents, not only keywords.
- [ ] Changes are annotated with deployment date and expected impact window.
- [ ] Before and after metrics are compared after enough crawl and ranking time has passed.

## 29. Common Anti-Patterns

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `GA4`, `CMS/code`, `Human/context`.

- [ ] One title template reused across many URLs.
- [ ] Meta descriptions generated from the first sentence without review.
- [ ] Multiple pages targeting the same query with no unique purpose.
- [ ] Thin AI-generated pages at scale.
- [ ] FAQ sections added only because they used to create rich results.
- [ ] Schema describing content not visible to users.
- [ ] JavaScript-only links and content with no render validation.
- [ ] Mobile pages missing desktop content.
- [ ] Canonicals pointing all variants to the homepage.
- [ ] Robots.txt used to hide sensitive content.
- [ ] Redirecting deleted URLs to the homepage.
- [ ] Over-optimized exact-match internal anchors.
- [ ] Images of important text.
- [ ] Popups blocking main content on mobile.
- [ ] Date-only freshness updates.
- [ ] "Best" listicles written to manipulate AI answers rather than help users choose.

## 30. Minimal Audit Flow

Evidence sources: `Firecrawl`, `Playwright`, `GSC`, `GA4`, `GKP`, `CrUX`, `LH`, plus vertical sources such as `GBP`, `GMAPS`, or `GMC` when relevant.

Use this fast path when the SEO agent needs to audit one page.

1. Identify page type, intent, audience, and business goal.
2. Check site architecture, page hierarchy, navigation, URL path, breadcrumbs, and internal-link role.
3. Check crawlability, status code, robots, canonical, sitemap inclusion, and internal links.
4. Compare raw HTML and rendered HTML for SEO-critical elements.
5. Review title, description, H1, headings, intro, and visible content.
6. Check mobile parity and Core Web Vitals.
7. Validate structured data against visible content.
8. Review image alt text, media, and accessibility basics.
9. Assess content usefulness, originality, trust, and freshness.
10. Check internal links and next steps.
11. Produce prioritized fixes with evidence and owner.
